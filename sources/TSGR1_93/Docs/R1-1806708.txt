Title: Summary of open issues on codeword mapping

Issues on codeword mapping and proposed resolutions

In this contribution, a summary of issues on codeword mapping raised in the five submitted contributions for RAN1#93 is given ([1]-[5]). The issues are of three kinds and outlined in Table 1, 2, and 3:

Critical issues: e.g. missing text/components in the specification

Specification refinement: e.g. clarification

Other issues: e.g. new proposals

The proposals for resolving issue 2.1 and 2.2 are intended to avoid ambiguities in specification on DMRS port definition and rate matching, respectively. Both proposals seem quite beneficial in improving the clarity of the specification.

Particularly for issue 2.2, while “rate matching around X” is a familiar short-hand terminology in RAN1, it is not a term that clearly describes a UE operation in generating an UL transmission or UE assumption on a DL transmission. This term can also be a misnomer in this particular context. For example, in 38.212, rate matching typically refers to an operation of processing an encoded bit steam via a buffer and truncating it accordingly. It is by no means obvious how this bit-level operation correlates with mapping a symbol stream to a set of available REs (where some REs are to be avoided).

The proposal for issue 2.1 is also supported by Ericsson.

On the other hand, Huawei dissents the necessity of 2.1 and 2.2 as follows:

Issue 2.1: “the TP is not needed. Since the related agreement already captured in Section 7.3.1.2.2 of 38.212. The previous wording here is only to say procedure to form the antenna ports, which is described in 38.214. So, no change is needed.”

Issue 2.2: “It is not an essential issue, rate matching is a clear and well known wording, which already defined in 212. If changed with “Not available RBs” it may be difficult to distinguish the case of “puncture””

Therefore, the following resolution is possible.

Proposal:

Issue 2.1: Briefly discuss if there is another objection on vivo’s text proposal

Issue 2.2: Briefly discuss if there is another objection on Ericsson’s proposal: replace “rate matched” with “not available for PDSCH” to align with section 5.1.4 terminology of TS 38.214

| Issue | Summary of proposal | Companies

For issue 3.1, the proposal from Ericsson is a reiteration of the non-agreeable components proposed in RAN1#92b (the condition involving CS-RNTI was agreed). The DCI-format-based condition proposal 3.1 is based on a concern that during scrambling seed reconfiguration ambiguity period (due to non-synchronized RRC), or if the RRC reconfiguration message is lost, the UE cannot be reached by any DCI format using C-RNTI.

On the other hand, Huawei, not agreeing to this proposal, argues as follows: “It has been discussed in last meeting, we do not think there is any issue for the configurable ID for data scrambling in current specs. Actually, for DMRS scrambling IDs, it was already agreed with first configured ID in fall back DCIs during last meeting.”

Likewise, issue 3.2 was briefly raised and discussed in RAN1#92b. The LTE-based TB-to-CW mapping was agreed. Therefore, the proposal from AT&T is essentially an extension of the previously agreed scheme.

Therefore, the following resolution is possible.

Proposal:

Issue 3.1: Discuss briefly if there is any new argument regarding the validity of issue 3.1 (building on the discussion in RAN1#92b)

If so, discuss whether Ericsson’s proposal is agreeable

Issue 3.2: Discuss if there is any tangible benefit from dynamic mapping proposal

If so, discuss whether AT&T’s proposal is agreeable
